## Bug 1：RAG 分类和地区标注完全失效

### 现象
数据库中 457 条政策数据里：
- 454 条 `region = '全国'`，只有 3 条有正确省份
- `category_l1` 使用了「科技/金融/医疗/建筑/教育/农业/能源/其他」这套分类，与前端 `policyTree` 完全不匹配
- 用户选择「广东 + 科技创新」生成报告，RAG 检索出来的结果是全国各地混杂，不精准

### 根本原因

**分类问题**：`app/crawler/base.py` 里的 LLM 分类 Prompt 写的是：
```
"category_l1":"科技/金融/医疗/建筑/教育/农业/能源/其他"
```
这是开发者随手写的分类，和前端 `policyTree` 里的 `资金支持/资质认定/科技创新/人才政策/产业发展/绿色低碳/对外贸易/创业扶持/科技竞赛/校企合作` 完全对不上。
用户在前端选「资质认定」，后端就去 `WHERE category_l1 = '资质认定'` 过滤，但数据库里根本没有这个值，导致过滤全部失效，回退到全库搜索。

**地区问题**：`base.py` 第 517 行直接硬编码：
```python
meta["region"] = "全国"
```
任何政策不管是广东省科技厅发的还是国家部委发的，全部写成「全国」，导致地区过滤完全无意义。

### 解决方案

**修复一：更新 LLM 分类 Prompt（`app/crawler/base.py`）**
把 Prompt 里的分类选项改成与前端完全一致的 11 个：
```
资金支持、资质认定、科技创新、人才政策、产业发展、绿色低碳、
对外贸易、创业扶持、科技竞赛、校企合作、其他
```
并在注释中说明每个分类的对应场景，防止 LLM 自由发挥。

**修复二：新增地区提取函数（`app/crawler/base.py`）**
编写 `_extract_region(url, title, publisher)` 函数，通过规则匹配从以下三个来源推断省份：
- URL 域名（如 `gdstc.gov.cn` → 广东）
- 发布机构名（如 `广东省科学技术厅` → 广东）
- 政策标题（如 `广东省…` → 广东）
覆盖 35 个省市直辖市，匹配不到时才默认「全国」。

**修复三：批量重标注历史数据（`relabel_db.py`）**
编写批量重标注脚本，对已入库的 457 条历史数据：
- 用 `_extract_region` 规则重新标注地区
- 用关键词规则（高置信度）+ LLM（低置信度兜底）重新分类
- 调用 `UPDATE policies SET region=$1, category_l1=$2 WHERE id=$3` 批量写入
- 同步更新 Elasticsearch 索引

### 修复效果

| 指标 | 修复前 | 修复后 |
|------|-------|-------|
| 有省份标注的政策数 | 3 条 | 253 条 |
| 省份覆盖率 | 0.7% | 55.4% |
| 分类与前端对齐 | 否（4类乱序）| 是（11类对齐）|
| RAG 分类匹配率（广东+科技）| 30% | **100%** |

## Bug 2：RAG 验证脚本卡死（DashScope embedding API 超时）

### 现象
`eval_rag.py`、`eval_rag_lite.py` 等评估脚本启动后永久卡住，没有任何输出，进程无法被 `taskkill` 终止。

### 根本原因
这些脚本需要调用 DashScope embedding API（阿里云）来把查询文本转成向量，再做相似度搜索。
但当前网络环境下，`dashscope.aliyuncs.com` 的请求没有响应（超时），Python 的 `requests`/`httpx` 默认没有设置超时时间，导致进程永久阻塞在网络 I/O 等待状态。

由于进程阻塞在系统内核的 socket 等待上，`taskkill /F` 也无法强制结束，必须重启才能清除。

### 解决方案
编写了不依赖任何外部 API 的纯数据库验证脚本 `eval_db_only.py`：
- 直接用 asyncpg 连接 PostgreSQL
- 取已存储的 `chunk.embedding` 作为"查询向量"，验证过滤 SQL 的逻辑正确性
- 展示分类/地区分布、Reflexion 状态等所有可验证项
- 完全不调用任何外部 API，不会卡死

## Bug 3：大量 Python 僵尸进程导致系统卡死

### 现象
因 DashScope API 超时，多次尝试运行评估脚本，每次都产生一个阻塞在网络 I/O 的僵尸进程。
最终积累了多个僵尸进程，导致：
- `taskkill /F /IM python.exe` 返回超时错误
- PowerShell 新命令也开始卡住
- uvicorn 启动时卡在 `INFO: Will watch for changes...` 不动

### 根本原因
Windows 上阻塞在 socket 等待的进程（未设置超时的网络请求）进入内核级等待状态，用户态的 `taskkill /F` 无权强制结束，需要重启操作系统才能清除。

### 解决方案
重启电脑，清除所有僵尸进程。

**预防措施**：所有脚本中的 HTTP 请求必须设置超时：
```python
httpx.AsyncClient(timeout=30)   # 正确
requests.get(url, timeout=30)   # 正确
requests.get(url)               # 错误，可能永久阻塞
```

## Bug 4：uvicorn 启动时持续刷屏 `error connecting in 'pool-1'`

### 现象
后端启动后，终端不断刷出：
```
error connecting in 'pool-1': Psycopg cannot use the 'ProactorEventLoop' to run in async mode.
```
每秒刷几十行，完全淹没正常日志，但服务器仍然能正常响应请求。

### 根本原因
LangGraph 的会话持久化使用 `psycopg3`（即 `psycopg` 包）的 `AsyncConnectionPool`。
而 uvicorn 在 Windows 上默认使用 `ProactorEventLoop`（Python 3.8+ 在 Windows 的默认策略），psycopg3 的异步模式与 `ProactorEventLoop` 不兼容。

之前的代码已经 `try/except` 捕获了初始化失败：
```python
except Exception as e:
    print(f"[LangGraph] Checkpointer 初始化失败，使用无状态模式: {e}", flush=True)
```
但问题在于：`AsyncConnectionPool` 内部有一个后台重试任务，即使抛出异常，这个后台任务仍然在事件循环里持续运行、持续失败、持续打印错误——因为异常只阻止了"池创建成功"，没有阻止池内部的重试协程。

### 解决方案
在 `app/agents/chat/graph.py` 中添加 `_is_proactor_loop()` 检测函数：
```python
def _is_proactor_loop() -> bool:
    import sys, asyncio
    if sys.platform != "win32":
        return False
    try:
        loop = asyncio.get_event_loop()
        return isinstance(loop, asyncio.ProactorEventLoop)
    except Exception:
        return False
```
在 `get_graph()` 的最开头判断：若检测到 ProactorEventLoop，**直接跳过 psycopg3 初始化**，不创建连接池，也就不会启动后台重试任务：
```python
if _is_proactor_loop():
    print("[LangGraph] Windows ProactorEventLoop，跳过 checkpointer（无状态模式）")
    _graph = build_graph(checkpointer=None)
    return _graph
```
这样既避免了错误刷屏，也明确告知使用无状态模式（对话功能正常，仅跨会话历史不持久）。

## Bug 5：Reflexion 优化器加载反馈失败

### 现象
手动触发 `POST /admin/reflexion/trigger?dry_run=false` 后，终端打印：
```
[Reflexion] 加载反馈样本失败: 'str' object has no attribute 'get'
```

### 根本原因
`optimizer.py` 的 `load_feedback_examples` 函数从数据库查询 `feedback` 表，
其中 `keywords` 字段是 PostgreSQL 的 `JSONB` 类型。

asyncpg 会把 JSONB 返回为 Python 字符串（`str`），而不是 `dict`。
但代码直接执行：
```python
kw = r["keywords"] or {}
kw.get("l1")   # 报错：str 没有 .get() 方法
```

### 解决方案
在使用前判断类型，若是字符串则先 `json.loads`：
```python
kw = r["keywords"] or {}
if isinstance(kw, str):
    try:
        kw = json.loads(kw)
    except Exception:
        kw = {}
```

## Bug 6：Reflexion 门槛"20条"只存在于说明文字，代码没有实际门槛

### 现象
验证脚本输出中写了「积累 20 条反馈才触发」，用户按照此逻辑测试，但实际代码中并没有这个判断，随时都会运行优化（只判断 golden set 够不够 5 条）。

### 根本原因
这个数字是在验证脚本 `eval_db_only.py` 的说明文字里写的，不是代码里的实际逻辑，属于文档和代码不一致。

### 解决方案
在 `app/reflexion/optimizer.py` 的 `run_optimization` 函数中，在 golden set 检查之后加入正式的反馈数量门槛：
```python
MIN_FEEDBACK = 10
if len(feedback_examples) < MIN_FEEDBACK:
    return {
        "status": "skipped",
        "reason": f"用户反馈不足（当前 {len(feedback_examples)} 条，需 {MIN_FEEDBACK} 条）",
    }
```
同时把说明文字里的「20条」改为「10条」，保持一致。
