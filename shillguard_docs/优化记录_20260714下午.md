## 第一阶段：声明级政策验证器

### 背景与问题

PolicyRadar 报告生成的旧版流程：

```
用户查询 → RAG 检索 12 条政策 → LLM 生成报告 → citation_verifier（事后校验）
```

**旧版 `citation_verifier.py` 的根本缺陷：**

事后校验只能检查"政策名称字符串是否出现在 context 中"（字符串匹配），完全无法处理两种政策 AI 领域特有的高风险错误：

- **时效错误**：LLM 引用了一条截止日期已过的政策，企业按此申报被退回，损失数月时间
- **政策矛盾**：同一类型下，广东省的补贴标准是 500 万元，国家标准是 100 万元，LLM 随机选了一个写进报告，用户无法判断哪个适用

这两类问题在"事后"根本无法纠正——LLM 在生成时已经把错误的数字融入了完整叙述中。

### 解决思路

来源于 CMU/Anthropic 2026 年提出的 VERA（声明级验证框架），结合政策领域的具体特征：

**核心范式转变：从事后校验 → 预生成注入**

```
旧：RAG 检索 → LLM 生成 → 检查（已经晚了）
新：RAG 检索 → 验证注入 → LLM 生成（看到的 context 已经带有正确标注）
```

### 实现方案

**新建文件：`app/agents/report/policy_verifier.py`**

包含三层验证，分别对应三种不同成本的技术手段：

#### ① 时效验证（纯规则，0 LLM 调用）

```python
def check_validity(policy: dict) -> PolicyValidity:
    today = date.today()
    deadline = _parse_date(policy.get("deadline"))
    pub_date = _parse_date(policy.get("pub_date"))
    
    if deadline and deadline < today:
        → status = "expired"，badge = "【已截止·2025-03-01】"
    elif deadline and deadline < today + 7天:
        → status = "expiring_soon"，badge = "【紧急·仅剩3天】"
    elif deadline and deadline < today + 30天:
        → status = "expiring_soon"，badge = "【即将截止·2025-01-20】"
    elif pub_date and 距今 > 2年:
        → status = "potentially_outdated"，badge = "【发布较久·建议核实】"
    else:
        → status = "active"，badge = ""
```

状态判断逻辑：先看 deadline 是否过期，再看 deadline 是否紧迫，最后看 pub_date 是否太旧。

#### ② 补贴金额矛盾检测（纯规则）

```python
def _detect_amount_contradictions(policies):
```

金额提取用正则，支持"500万元"、"2亿"、"300万"等格式，全部转换为"万元"单位后比较。

#### ③ 申报条件矛盾检测（1次批量 LLM 调用）

```python
async def _detect_condition_contradictions(policies):
    # 只取 active 状态且有 key_conditions 的政策
    # 按 category_l1 分组，只检测 2 条以上的组
    # 最多取 3 组 × 3 条 = 9 条，合并成 1 个 prompt

```

整个验证批次只产生 **最多 1 次 LLM 调用**，且仅用于条件矛盾检测这一最需要语义理解的场景。

### 结果注入

验证完成后，`format_verified_context()` 函数将结果写入 context 字符串：

```
【⚠️ 政策矛盾预警 - 请在报告中明确标注以下差异】
  - 【补贴金额差异】同为「资质认定」类，《广东省高企认定补贴》补贴最高500万元，
    而《国家高新技术企业认定奖励》为100万元，相差400%。

[政策1] 【即将截止·7天】《广东省高企认定补贴》
  发布单位：广东省科技厅  地区：广东
  申报截止：2025-01-20  补贴金额：最高500万元
  ⏰ 时效提示：申报截止2025-01-20，剩余7天，请抓紧准备材料
  
[政策2] 【已截止·2024-03-01】《某过期政策》
  ...
  ❌ 此政策已截止，不建议列为重点推荐
```

LLM 在看到这个 context 时，矛盾和时效信息已经是显式标注的，不需要"推断"，从而极大降低报告中出现时效错误和矛盾遗漏的概率。

## 第二阶段：数据链路梳理与报告入库

### 背景与问题

用户提问：

> "RAG 检索 12 条候选政策，这些 12 条验证的数据以及结果会在最终的报告中展示吗？然后跟着报告一起进入数据库？还是说怎么保存？"

对这个问题进行了全面的链路梳理，发现一个关键的**数据断层**：

**旧版 `query_logs` 只存储了用户查询意图（keywords + user_input），不存储生成的报告内容和验证元数据。**

这意味着 Reflexion 优化器只能知道"用户对这个关键词组合打了3星"，但完全不知道"那次报告写了什么内容、发现了几个矛盾、哪些政策被引用"。Reflexion 的优化针对性因此受限。

### 完整链路梳理

```
数据来源（爬虫写入，一次性）：
  policies 表     ← 政策全文 + 向量 + 元数据
  policy_chunks 表 ← 512字分块向量（RAG精准检索）
  Elasticsearch   ← BM25全文索引

实时生成链路（每次生成报告）：
  query_logs ← INSERT(session_id + keywords + user_input)   ← 请求开始时写入
  │
  ├── RAG 检索（读操作，不写入）
  ├── 验证（内存，不写入）
  ├── LLM 生成（内存，不写入）
  └── SSE 流推送给前端
  │
  query_logs ← UPDATE(report_text + verification_meta)      ← 流结束时写入
  │
  前端 ← 渲染报告 → localStorage（历史记录）

用户评分：
  feedback 表 ← INSERT(session_id + score + signal_type)

Reflexion 优化（离线，每周）：
  JOIN feedback + query_logs → 低分样本
  → DSPy MIPROv2 优化 prompt
  → reflexion_patches 表 ← 优化结果
```

### 实现：报告全文和验证元数据入库

**修改一：`app/db/init.py`**

使用 `IF NOT EXISTS` 保证幂等，可重复执行不报错。

`stream_report()` 新增 `out_meta: dict | None = None` 参数。图运行完成后，将验证结果写入这个可变字典：

**修改三：`app/api/report.py`**

`_event_stream()` 函数改为两阶段写入：

```python
async def _event_stream(keywords, user_input, module, session_id):
    out_meta = {}
    full_report = []
    
    # 阶段1：流式输出 token，同时攒齐完整报告
    async for token in stream_report(keywords, user_input, module, out_meta=out_meta):
        full_report.append(token)
        yield f"data: {json.dumps({'type': 'delta', 'content': token})}\n\n"
    
    yield 'data: {"type":"done"}\n\n'
    
    # 阶段2：流结束后异步写入（不阻塞前端已收到的报告）
    asyncio.create_task(_save_report(session_id, "".join(full_report), out_meta))
```

`_save_report()` 执行 UPDATE 而非 INSERT（`_log_query()` 已经在请求开始时 INSERT 过了）：

```python
async def _save_report(session_id, report_text, verification_meta):
    UPDATE query_logs
    SET report_text = $1, verification_meta = $2::jsonb
    WHERE session_id = $3
```

## 第三阶段：2026 年前沿 Agent 技术调研

### PolicyRadar 的核心差异点（对比市场竞品）

市场上的政策 AI 产品基本分三类：

| 类型 | 代表逻辑 | 核心缺陷 |
|------|---------|---------|
| 搜索增强型 | 网页搜索 + LLM 总结 | 无私有知识库，无法追踪地方细则 |
| 简单 RAG 型 | 文档向量化 + 问答 | 全文向量检索精度差，无过滤 |
| 固定模板型 | 人工整理 + 关键词匹配 | 无自然语言问答，更新滞后 |

PolicyRadar 的真正差异点：

1. **混合 RAG + 元数据过滤**：pgvector + BM25 + RRF + region/category_l1 SQL 预过滤，检索精度远超单一向量检索
2. **512字 Chunk 级向量 + 全文存储**：两者兼顾，市面上大多数只选其一
3. **DSPy MIPROv2 Reflexion 闭环**：用户反馈自动优化 prompt，垂直政策 AI 领域极少见
4. **声明级政策验证**（本次实现）：时效+矛盾检测，在生成前注入，行业空白
5. **三层记忆**：滑动窗口 + LLM 摘要 + mem0 跨会话，大多数竞品无跨会话记忆

### 2026 年顶会论文重点技术

**COMPASS（Google，ACL 2026）**

三角色分层架构，解决长程任务中 Agent 丢失焦点的问题：

- Main Agent：执行推理和工具调用（做事）
- Meta-Thinker：监控进度，发现偏航时主动干预（想大局）
- Context Manager：维护压缩后的上下文摘要（记忆管家）

在 GAIA/BrowseComp 等 Benchmark 上比单 Agent 提升 **20%** 准确率。

*PolicyRadar 适用场景*：Chat Agent 的多轮对话中加入 Meta-Thinker，主动发现对话偏离政策问题时拉回焦点。

**D2PLAN（ACL 2026）**

双 Agent 协作：Reasoner 构建推理计划，Purifier 过滤无关证据。核心发现：单 Agent 在检索到 10+ 文档时容易被无关信息"劫持"推理。

*PolicyRadar 适用场景*：检索质量评分（Purifier 角色），过滤噪声文档。→ **本次已实现（Grader 节点）**

**Reflective RAG（ACL 2026 Findings）**

检索 → 反思标签评分（relevance + faithfulness + confidence） → 分数低则重新检索 → 达标才进入生成。用 GRPO 强化学习训练评估组件本身。

*PolicyRadar 适用场景*：Grader 的进阶版，用强化学习让评分器本身越来越精准。

**NeuroCausal-RAG（开源，2025年4月）**

因果知识图谱 + 多跳检索 + 矛盾检测 + 时序推理，专门为跨文档矛盾场景设计。与政策矛盾检测思路高度吻合。

**LLM-Wiki / Error Book 模式（arxiv 2026）**

在知识库构建阶段引入持久错误修正机制：Error Book 记录已知错误模式，每次爬取时自动检测并修复。

*PolicyRadar 适用场景*：爬虫入库时检测是否有同一发布单位的旧版本，自动标注旧版本为"可能已被更新"。

### 可借鉴技术优先级

| 优先级 | 技术 | 实施成本 | 价值 | 状态 |
|--------|------|---------|------|------|

## 第四阶段：Retrieval Grader 实现

### 背景与问题

RAG 检索返回的 12 条政策中，通常有 3-5 条是因 RRF 融合或向量相似度"凑数"进来的，与用户真实需求相关性低。直接将 12 条全部传给 LLM 的问题：

1. **浪费 context 窗口**：无关内容降低 LLM 对关键信息的注意力
2. **制造幻觉来源**：LLM 看到不相关政策的数字后，可能错误地将其混入生成结果
3. **增加 token 成本**：无用的 context 带来额外开销

### 解决方案设计

将两个功能合并成 **1 次 fast_llm 调用**，实现最优成本效益比：

- **Grader 部分（Self-RAG 思想）**：对每条政策打 0-10 分，过滤 score < 5 的文档
- **Purifier 部分（D2PLAN 思想）**：对 score ≥ 5 的政策，提取核心事实（50字内）

### 技术约束与设计决策

| 问题 | 解决方案 | 原因 |
|------|---------|------|
| DeepSeek 结构化输出兼容性 | 不用 `with_structured_output`，改为手动 JSON 解析 + regex 容错 | `with_structured_output` 依赖 OpenAI function calling，DeepSeek 兼容性不稳定 |
| prompt 长度控制 | 每条政策紧凑描述 ≤100字，12条 ≈1200 token | 控制成本，避免超出上下文限制 |
| LLM 超时/失败 | 15s timeout + try/except，任何异常降级返回原始列表 | 保证主流程不受影响 |
| 过度过滤风险 | `MIN_KEPT=3` 保底 | 即使全部低分也保留最高的3条，避免生成报告无内容可用 |
| 超出批处理上限 | `MAX_INPUT=12`，超出部分追加到末尾（未评分） | 控制单次 prompt 大小 |

### 评分标准（Prompt 设计）

```
9-10：精准命中，政策主题、地区、支持对象与需求高度一致
6-8 ：高度相关，包含用户所需关键信息（金额、条件、截止日期等）
3-5 ：部分相关，话题接近但细节不匹配（如行业不符、地区不同）
0-2 ：关联度低，基本无法为该用户提供有价值信息
```

### 实现文件：`app/rag/grader.py`

核心函数 `grade_and_filter(policies, keywords, user_input)` 的执行流程：

```python
1. 构建紧凑 prompt：
   用户需求 = keywords(l1/l2/l3/region/company_size) + user_input
   政策列表 = 每条政策的title + 属性(类别/地区/补贴/截止) + 摘要(前100字)

2. fast_llm.ainvoke（temperature=0，max_tokens=1000，timeout=15s）

3. 解析 LLM 返回的 JSON：
   {"grades": [{"idx": 0, "score": 8, "key_facts": "最高补贴500万元..."}, ...]}
   容错处理：regex 提取 JSON 块 + 非法条目过滤

4. 过滤：
   passed = [p for p in policies if grade_map[i].score >= GRADE_THRESHOLD(5)]
   if len(passed) < MIN_KEPT(3):
       sorted_all = sorted by score desc
       passed = top MIN_KEPT

5. 注入字段到每条保留的政策：
   policy["grader_score"] = 8
   policy["graded_key_facts"] = "最高补贴500万元，需高企认定，截止2025-03-15"

6. 降级 fallback：超时/JSON解析失败 → 返回原始 policies（不损失功能）
```

## 完整的最终报告生成流程

```
用户选择关键词（地区/类别/公司规模）+ 输入企业描述
  │
  ▼ POST /api/v1/report/generate
  
① query_logs INSERT(session_id, keywords, user_input)
  
② retrieve_node [~800ms]
   pgvector 向量检索（metadata过滤）+ Elasticsearch BM25
   RRF 融合 + Reranker 重排
   → 12 条候选政策
  
③ grade_policies_node [~3000ms] ← 本次新增
   fast_llm 批量评分(0-10) + 核心事实提取
   过滤 score<5 的噪声文档
   → 8 条高质量政策（带 grader_score + graded_key_facts）
  
④ verify_policies_node [~2000ms] ← 第一阶段实现
   时效验证（规则，0 LLM）: expired/expiring_soon/active
   金额矛盾检测（规则）: 同类政策补贴差异 >50%
   条件矛盾检测（1次LLM）: 批量检测申报条件冲突
   → VerificationResult（validity_map + contradictions）
  
⑤ format_context_node [<100ms]
   组装带注释的 context 文本：
   - 矛盾预警（前置）
   - 每条政策：🎯核心摘要 + 时效标签 + 结构化信息
   System prompt 注入：expired_count + contradiction_count
   → 发给 LLM 的 messages
  
⑥ LLM 流式生成 [~5000ms]
   看到的 context 已经是：
   - 过滤了噪声的 8 条（Grader）
   - 带有时效标签的（Verifier）
   - 带有矛盾预警的（Verifier）
   - 每条政策的核心事实已经提炼好（Purifier）
   → 生成结构化报告（6个章节，含"政策差异说明"强制节）
  
⑦ citation_verifier（事后保底）
   字符串级幻觉检测，若有未在 context 中出现的引用，追加"待核实"标注

⑧ SSE 推送给前端 → 前端渲染 + localStorage 持久化

⑨ _save_report [异步，不阻塞前端]
   query_logs UPDATE(report_text, verification_meta)
   日志输出：报告已入库 session=xxx 字符=N 矛盾=M 过期=K
```

## 遗留问题与后续规划

### 待实现（近期）

1. **COMPASS Meta-Thinker**：为 Chat Agent 加入对话质量监控，主动发现并纠正偏离政策主题的对话
2. **Error Book 爬虫版本检测**：爬取新政策时自动检测同一发布单位的旧版本，标注"可能已被更新"

### 待实现（长期）

3. **政策关系图谱**：建立政策间的显式关系（supersedes / implements / restricts / expands），支持"政策链"查询（国家标准→省级实施细则→地市补充规定）
4. **Reflexion 强化**：利用现在入库的 report_text 和 verification_meta，为 Reflexion 优化器提供更丰富的训练信号

### 当前系统的潜在风险点

1. **Grader 的 fast_llm 耗时**：新增了约 2-4 秒的时延。可以考虑和 Reranker 步骤合并，或降低 MAX_INPUT
2. **`_parse_grades` 容错**：当前 JSON 解析对格式异常有兜底，但若 LLM 输出完全不是 JSON（如被截断），会直接降级到原始排序。建议监控降级发生频率
3. **政策矛盾阈值**：当前金额矛盾阈值为 >50% 差异，可能对"国家100万元 + 省级配套500万元（叠加而非矛盾）"的情况误报。后续可增加"叠加关系判断"逻辑
4. **`query_logs.report_text` 存储成本**：每份报告约 2000-5000 字符，百次请求约 200KB-500KB。PostgreSQL TEXT 类型无压缩，数据量大后需评估是否改用对象存储
