# Locust 指标定义与分析（小白讲解版）

> 日期：2026-07-07
> 用途：压测时对照查阅，搞懂 Locust 里每个参数、每个结果列的含义
> 贯穿比喻：你的 chat agent = 一家奶茶店，Locust = 派假顾客来挤你店的工具

---

## 一、性能测试在测什么

你开了一家奶茶店（chat agent），想知道：**如果同时来 1000 个顾客，我的店扛得住吗？**

性能测试 = **模拟很多假顾客同时来点单**，看你的店会不会崩、会等多久、能服务多少人。Locust 就是那个"派假顾客的工具"。

---

## 二、Locust 的输入参数（启动表单填的框）

### 1. Number of users（并发用户数）

**= 同时有多少个假顾客站在你店里点单。**

- 填 10 = 模拟 10 个顾客同时在点单
- 填 1000 = 模拟 1000 个顾客同时挤进来

注意：这不是"一共来 1000 个"，而是"同一时刻有 1000 个同时在店里"。一个顾客点完单拿到奶茶后，他会**再点下一杯**（循环），始终保持在店里有 1000 个人。

### 2. Ramp up（加压速率）

**= 每秒放进来几个顾客。**

- 填 2 = 每秒进店 2 个顾客
- 填 50 = 每秒进店 50 个

为什么要这个？如果目标是 1000 顾客，**不能瞬间把 1000 个人全塞进去**——那一瞬间店门会被挤爆，分不清是"店不行"还是"进门太猛"。所以慢慢加：每秒进 50 个，20 秒后才到 1000 个，给店铺一个适应过程。

### 3. Host（被测地址）

**= 你的店在哪条街。** `http://localhost:8000` 就是你的 FastAPI 服务。

---

## 三、STATS 表里的请求名（Name 列）

脚本里模拟了**两种行为**，所以表里有几行不同的 Name：

### 1. `chat_stream` —— 模拟顾客点奶茶（完整一杯做完）

**主测试**：假顾客发一句"你好"给 chat agent，agent 调 LLM 流式回答。这一行记录的是**从发消息到整个回答结束**的总耗时。

### 2. `chat_stream_TTFT` —— 只量"第一口奶茶多久端上来"

**TTFT = Time To First Token = 首字返回时间**。

拆开这个词：
- **Time** = 时间
- **To** = 到
- **First** = 第一个
- **Token** = "字"（LLM 吐出来的一个片段）

合起来：**从你发消息那一刻，到收到 AI 吐出的第一个字，中间等了多久。**

为什么单独量这个？因为用户感知"快不快"**全看第一个字多久出现**：
- 0.5 秒开始打字 → 用户觉得"哇好快"
- 7 秒才开始打字 → 用户以为卡死了，已经想关页面

**TTFT 是 AI 产品最关键的体验指标**，比总耗时更重要。业界目标一般是 **<500ms（0.5 秒）**。本项目单请求是 7 秒，已偏慢；10 并发变 30 秒，用户早跑了。

> 比喻：你点奶茶，**从点单到店员递给你第一口试饮**的时间 = TTFT。后面的总耗时是从点单到整杯做完。

### 3. `chat_stream_TPS` —— 量"做奶茶的速度"

**TPS = Tokens Per Second = 每秒吐多少字。**

LLM 流式回答时，是不断一个字一个字吐出来的。TPS 衡量**吐字速度**——TPS 越大，用户看到字蹦得越快越流畅。本项目大概 5-17 字/秒。

> 比喻：店员做完一整杯奶茶后，往你杯里倒的速度。倒得快 = TPS 高 = 用户看着流畅。

### 4. `health` —— 探活对照（不点奶茶，只问"店还开着吗"）

`/health` 是 FastAPI 里的一个**最简单的接口**：

```python
@app.get("/health")
def health():
    return {"status": "ok"}
```

它**不连数据库、不调 LLM、不做任何重活**，就是立刻返回"ok"。正常情况下它应该**永远 10 毫秒以内**返回。

**为什么要测它？它是"照妖镜"。**

逻辑：
- 如果 `/chat`（点奶茶）变慢了，但 `/health`（问店开没开）**还是飞快** → 说明是**奶茶制作环节慢**（LLM/RAG 慢），店本身没毛病
- 如果连 `/health` 都变慢了 → 说明**整个店的服务员（事件循环）都被占住了**，连回答"店开着吗"都来不及 → 这是**最严重的问题**，说明事件循环被堵死

本项目实测：health 从 14ms 涨到 120ms（1000 并发）。**连"问店开没开"都慢了 8 倍**，证明事件循环被 chat 的同步调用堵住了。这就是 health 的价值——它告诉你"病在店本身，不只是奶茶做得慢"。

## 四、STATS 表各列含义

### 1. `# Requests`（请求数）

**= 60 秒里一共发出了多少个这种请求。**

比如 `chat_stream` 在 10 并发时是 67，意思是 60 秒内 Locust 一共发了 67 次聊天请求。

### 2. `# Fails`（失败数）

**= 多少个请求失败了。**

什么叫失败？脚本里定义了：30 秒没收到第一个字、连接断、HTTP 不是 200，都算失败。

### 3. `Requests/s`（RPS，每秒请求数）

**= 每秒能处理几个请求。**

= 请求数 ÷ 60。这个数越高，说明服务吞吐量越大。10 并发时 chat 的 RPS 是 0.2，意思是**每秒只能完成 0.2 个聊天**——极低，因为每个聊天卡 30-40 秒。

> RPS 是"店的吞吐能力"核心指标。1000 并发下 RPS 还是上不去 = 店被堵死了。

### 4. `Average`（平均响应时间）

**= 所有请求耗时的平均值，单位毫秒。**

⚠️ **这个数会骗人，不要只看它**。原因见下面 p95 的讲解。

### 5. `Min / Max`（最小 / 最大耗时）

最短的那个请求多久、最长的那个多久。Max 偶尔大正常，但持续大说明有问题。

## 五、重点：p50 / p90 / p95 / p99 是什么（那个 "p"）

**这是整个性能测试里最重要的概念。**

### "p" = Percentile = 百分位

**百分位的意思是：把所有请求按耗时从快到慢排序，看"排在某个百分比位置"的那个请求花了多久。**

用奶茶店举例。假设来了 100 个顾客，把他们的等待时间从短到长排成一列：

```
第 1 名（最快）：2 秒
第 2 名：3 秒
...
第 50 名：10 秒   ← p50（中位数）：一半人比他快，一半人比他慢
...
第 90 名：25 秒   ← p90：90% 的人比他快，只有 10% 比他慢
第 95 名：35 秒   ← p95：95% 的人比他快，只有 5% 比他慢
第 99 名：60 秒   ← p99：99% 的人比他快，只有 1% 比他慢
第 100 名（最慢）：120 秒
```

所以：
- **p50 = 中位数**：排在正中间那个人的耗时。"典型用户体验"
- **p95**：排在第 95% 那个人的耗时。"最倒霉的 5% 用户体验"
- **p99**：排在第 99% 那个人的耗时。"最倒霉的 1% 用户体验"

### 为什么不看 Average（平均）只看 p95/p99

**平均会骗人**。看个例子：

100 个顾客里：
- 90 个等 1 秒
- 10 个等 100 秒

平均 = (90×1 + 10×100) / 100 = **10.9 秒** ← 看着还行？

但真实情况是：**有 10 个顾客等了 100 秒，他们早就骂街走了**。平均数把"大部分快+少部分极慢"抹平了，掩盖了问题。

而 p95 = 100 秒（那 10 个倒霉蛋的耗时），**直接暴露了"有 5% 的人等 100 秒"这个真相**。

> **业界铁律：性能优化只看 p95 和 p99，不看平均。** 因为 p95/p99 代表"最差的用户体验"，而你要保证的是"即使是最倒霉的用户也不能太慢"。

### 本项目实测怎么读

以 10 并发为例：

| 指标 | 值 | 含义 |
|---|---|---|
| chat p50 | 37000ms | 一半的聊天请求等 37 秒 |
| chat p95 | 120000ms | 5% 的聊天请求等 **2 分钟** |
| chat p99 | 146000ms | 1% 的聊天请求等 **2.4 分钟** |
| TTFT p50 | 30000ms | 一半的请求 30 秒才吐第一个字 |
| TTFT p95 | 54000ms | 5% 的请求 54 秒才吐第一个字 |

**翻译成人话**：10 个并发用户里，一半人等 30 秒才看到 AI 开始打字，5% 的人等快 2 分钟。这种体验，用户早就跑了。

## 六、基线数据大白话翻译

| 并发 | 大白话 |
|---|---|
| **1 人** | 一个人用，7 秒开始打字，9 秒答完。能用，但偏慢。 |
| **10 人** | 十个人同时用，一半人等 30 秒才看到第一个字，5% 的人等 2 分钟。**55% 的人直接失败**（30 秒一个字都没有）。 |
| **100 人** | 一百人同时用，**100% 失败**，连一个能用的都没有。 |
| **1000 人** | 一千人挤进来，**100% 失败**，而且连"问店开没开"都要等 470ms（原来 14ms）。店瘫痪了。 |

**结论**：chat agent 现在**只能撑 5 个人同时用**，10 个人就开始大规模失败。问题出在代码里用了同步调用（`llm.invoke()`），把事件循环堵死了。

## 七、基线核心数据对照表

| 并发 | chat 失败率 | chat p95 | TTFT p95 | health p50 | 翻译 |
|---|---|---|---|---|---|
| 10 | 55% | 120s | 54s | 14ms | 一半人失败，幸存者等 54 秒才出字；店还正常（health 快） |
| 100 | 100% | 42s | 42s | 34ms | 全失败；店开始变慢（health 2.4×） |
| 1000 | 100% | 55s | 55s | 120ms | 全失败；店本身都堵了（health 8.6×） |

**核心诊断**：
1. chat p95 几十秒 → 同步阻塞，请求排队
2. health p50 从 14ms 涨到 120ms → 事件循环被堵死（店本身都病了）
3. 失败全是"30 秒 0 字" → 不是 LLM 限流、不是数据库，是应用层同步调用堵的

## 九、看 Locust 结果的标准流程

1. **先看 Fails**：失败率是不是 0？不为 0 就有问题，优先解决。
2. **看 p95 / p99**（不看 Average）：最倒霉的用户等多久？能不能接受？
3. **对比 chat 和 health**：
   - health 不变慢、chat 慢 → LLM/RAG 环节慢
   - health 也变慢 → 事件循环被堵（最严重）
4. **看 RPS**：并发加上去后 RPS 涨不涨？不涨 = 到吞吐拐点了。
5. **看 Failures 标签页**：点进去看具体错误信息（429/Timeout/ConnError 各代表不同病因）。
